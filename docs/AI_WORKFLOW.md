# AI 工作流（单 PRD 模型）

> 本项目以 [`docs/prd/PRD-0002-rgbbox-project-catalog.md`](./prd/PRD-0002-rgbbox-project-catalog.md) 为**唯一**的 PRD 文档。
> 任何新功能、bug 修复、重构、迁移都**追加 R-N 条款**到对应章节。
> 详细目录见上述 PRD。
> 历史 PRD-0001（多 PRD 流程）已被本流程取代，状态 `superseded`，保留作历史。

---

## 1. 流程（极简版）

1. **提需求** → AI 在 PRD-0002 对应章节末尾追加 R-N 条款（ID 取下一个未用号）。
2. **实施** → 改完代码。
3. **自检** → 把 R-N 状态从 ⏳ 改为 ✅，附证据（命令输出 / 文件路径 / 测试结果）。
4. **用户验证** → 通过则 ✅ 保留；失败则在 PRD §8「已知问题」追加条目，R-N 改回 ⏳ 循环修。

---

## 2. 跳过白名单（不强制追加 R-N）

- 纯拼写 / 笔误修复（≤ 5 字符）；
- 仅改注释 / JSDoc / 文档格式；
- 仅改 `.gitignore` 增删路径；
- lockfile 重新生成（`package-lock.json` / `pnpm-lock.yaml`）的非语义 diff。

**"行为变更"必须有 R-N**——包括但不限于：

- 修改条件 / 循环 / 类型签名；
- 新增 / 删除 / 重命名导出；
- 改 IPC 通道、协议、状态结构；
- 改用户可见的 UI 行为；
- 改 `package.json` 的 scripts / deps；
- 改 `.github/workflows/*` 的 CI 行为。

AI 拿不准时，**默认追加 R-N**。

---

## 3. R-N 状态符号

| 符号 | 含义 |
| --- | --- |
| ⏳ | 待实施 |
| 🔄 | 实施中 |
| ✅ | 实施并自检通过（附证据） |
| ⚠️ | 部分通过 / 有 caveat |
| ❌ | 失败，已记入 §8 已知问题 |
| — | 不适用 |

R-N 写完后**必须**填一个初始状态（默认 ⏳）。

---

## 4. 提交规范

- 标题：`[PRD-0002] <type>: <subject>`
  - 例：`[PRD-0002] feat: add webgpu preview renderer`
  - 例：`[PRD-0002] fix: prevent media:// path traversal`
  - `type` 沿用 Conventional Commits：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `style` / `perf` / `build` / `ci`。
- 一个 R-N 可以跨多次 commit，commit 标题 ID 固定 `PRD-0002`。
- 不强制使用 PR 流程；如使用，描述里 link R-N 的章节。

---

## 5. AI 自我检查清单（每次准备改代码前过一遍）

```
□ 我要加的 R-N 是不是有具体 ID？加到对章节了吗？
□ 跳过白名单能不能 cover？不能 → 必须追加 R-N
□ 我准备用的提交标题是不是 [PRD-0002] 开头？
□ 自检后我会更新 R-N 状态为 ✅ 并附证据吗？
```

任何一项打勾失败 → **停下**，先补 R-N 再改代码。

---

## 6. 反例

- ❌ "顺手把 X 也改了"——除非 X 已在某条 R-N 范围内；
- ❌ "为了修这个 bug 我重构了 5 个文件"——重构需独立 R-N；
- ❌ "用户没明说但我觉得应该 X"——X 应在 R-N 的描述里讨论，等用户批准；
- ❌ "先开新 PRD-0003"——禁止，全部追加到 PRD-0002；
- ❌ "改完跑通了就关掉 R-N"——必须经用户在 Step 4 确认。

## 7. 流程元规则

- 本文件本身的修改属于"流程变更"，需要新开一份 PRD（不，本流程下没有新 PRD）→ 流程变更需用户**显式批准**才能动 `docs/AI_WORKFLOW.md` 本体。
- 仓库根 `CLAUDE.md` / `AGENTS.md` / `.github/copilot-instructions.md` 是入口，详细规则以本文件 + PRD-0002 为准。
- 当多个文件描述冲突，**以 PRD-0002 的 R-N 为准**。

## 8. Auto 模式（批量任务 / 低风险变更）

> 适用场景：用户授权 AI 自主跑完 R-N → 实施 → 自检全流程，**无需每步审批**。
> **触发关键词**：`auto` / `信任模式` / `自动跑完` / `批量修` / `auto 模式` / `auto L0` / `auto L1`。
> 详细定义见 [`docs/prd/PRD-0002-rgbbox-project-catalog.md`](./prd/PRD-0002-rgbbox-project-catalog.md) **R10**。

### 8.1 风险分级

| 级别 | 含义 | AI 行为 |
| --- | --- | --- |
| **L0** | 纯文档 / 注释 / `.gitignore` / lockfile 重新生成 / 测试添加（不改行为） | **无需审批**，直接执行，状态改 ✅ + 证据 |
| **L1** | 单文件改动 / 内部重构（行为不变 + 有测试覆盖）/ 不涉及 IPC / 安全 / engine / UI 核心 / 依赖 的小行为变更 | **一次审批**：列齐 R-N → 用户批 → AI 跑完，批量 ✅ |
| **L2** | IPC 通道、media:// 等安全敏感 / engine 逻辑 / UI 用户可见行为 / 新增/升级依赖 / 跨多文件架构 | **不在 auto 范围**，走 §1 标准四步 |

### 8.2 流程差异

- **L0**：AI 在 R-N 状态改 ✅ + 证据，**用户可批末审**。
- **L1**：AI 一次性把 R-N 列齐（描述里写明文件 + 子项），**用户批一次** → AI 自动跑完 → 完成后批量报 ✅ + 证据。
- **L2**：走 §1 标准四步，每步用户审。

### 8.3 退出 / 暂停

- 用户随时可说 `退出 auto` / `恢复手动` → 立即回 L2 全流程。
- L0 / L1 任何一次失败 → **暂停 auto**，单条 R-N 走四步。
- 同一会话 auto 模式连续 3 个 R-N 失败 → **强制回 L2**。

### 8.4 强制要求

- auto 模式下 R-N 描述必须列清**所有受影响文件 + 子项 R-条款**（让用户一眼看到范围）。
- 提交标题仍为 `[PRD-0002] ...`，不变。
- 即便 L0 / L1，AI 仍必须在完成后更新 R-N 状态为 ✅ + 证据，**不可跳过自检**。
- **不确定风险等级时，AI 应主动询问用户（L0/L1/L2？），不可擅自决定。**

### 8.5 AI 自我检查新增项

```
□ 用户是否说了 auto 模式关键词？
□ 当前任务属 L0 / L1 / L2 哪一级？（不确定时询问）
□ L1 模式下是否一次性列齐所有 R-N / 文件？
□ auto 模式下 R-N 描述是否包含完整文件清单？
```
